# PitchLens 功能偏差改动技术路线

对应《实时唱歌音高监测软件技术路线与实现方案》的差距清单与实施路线。
每项给出：现状 → 差距 → 改法（含涉及文件）→ 验收标准 → 预估工作量。

优先级说明：

- **P0**：会产生错误结果或错误传播的，先改。
- **P1**：方案明确承诺、用户可感知的功能缺口。
- **P2**：健壮性 / 工程质量改进。

2026-11-03 已修复的 bug（附点导出、meta BPM 粘连、校正表格错位、fps 统计）不在本文档范围。

## P0-1 连音线 / 延音线（弧线）识别

**现状**：代码中完全没有弧线处理。更危险的是：弧线顶部近水平段长度一旦超过 `h_len`（`recognition.py` 中 `split_line_masks`，约 `w * 0.018` ≈ 27px），会被水平线内核提取出来，在 `_assemble_notes` 里被判为增时线 dash，给前一个音符多加一拍——**错误会静默进入时值，只有小节校验可能兜住**。

**方案依据**：§5.2 上区符号含连音线/延音线；§5.3 要求校验"连音线与延音线是否混淆"。

**改法（分两期）**：

第一期（止血，0.5 天）：
1. 在 `recognition.py` 增加弧线检测：对 `binary` 中数字上方的连通域，按"宽 > 1.2×dh、高 < 0.6×dh、填充率低（空心弧）、上下边缘曲率"筛选弧线候选。
2. 检出的弧线区域从 `h_lines` 掩膜中剔除（`cv2.subtract`），杜绝误判为 dash。
3. 弧线本身暂不解释语义，在校正界面中提示"检测到 N 条连音线/延音线，请人工确认时值"。

第二期（语义，2–3 天）：
1. 弧线两端点各找一个最近数字（水平距离 < 0.8×dh）。
2. 两端音级相同 → 延音线（tie）：合并为一个 `NoteEvent`，时值相加，bbox 取联合；音级不同 → 连音线（slur）：不合并时值，在 `NoteEvent` 加 `slur_to_next: bool` 字段（可选，仅显示）。
3. 在 `score.py` 的 `validate()` 中增加：延音线两端音高不同 → 警告。

**涉及文件**：`pitchlens/core/recognition.py`（检测+剔除）、`pitchlens/core/score.py`（字段+校验）、`pitchlens/ui/score_view.py`（弧线叠加显示，可选）。

**验收**：
- 构造含弧线的测试图：弧线不再产生多余 dash，小节时值校验通过。
- 延音线合并后 `Score.total_beats` 与手工标注一致。

## P0-2 真实简谱测试集

**现状**：识别测试只用 `demo.py` 自渲染图片——自己画自己认，证明不了对真实图片的能力。

**方案依据**：§8 阶段 2 明确要求"使用实际会导入的简谱图片建立测试集"；§9 要求分别统计定位/音高/节奏/时值正确率。

**改法（1–2 天，持续扩充）**：
1. 收集 15–30 张真实印刷简谱（不同书籍/网站截图/字体），放入 `tests/fixtures/jianpu/`。
2. 每张配一个 `*.expected.txt`（现有简谱文本格式即可作为 ground truth）。
3. 新增 `tests/test_recognition_real.py`：识别结果与 expected 对比，输出四项指标——音符定位率（bbox 数量与顺序）、音级正确率、时值正确率、小节时值通过率。
4. 指标不达标不 fail 测试，而是输出报告（如 `pytest -s` 打印或写 JSON），先建立基线再定阈值。

**涉及文件**：新增 `tests/fixtures/`、`tests/test_recognition_real.py`。

**验收**：每张图能看到四项指标；基线数据写进 README"已知限制"一节。

## P1-1 符号分类器：模板匹配 → 轻量 CNN

**现状**：`TemplateClassifier` 用 Windows 系统字体渲染模板做 ZNCC 匹配。实测 `=` 被误分为 `0`、`P` 误为 `F`。换字体/拍照即失效。

**方案依据**：§5.2 "数字和元信息：轻量 CNN 分类"。

**改法（3–5 天）**：
1. 数据：用现有 demo 渲染器 + 字体/字号/加粗/噪声/模糊/旋转数据增强，程序化生成 0–7、#、b、=、/ 各数千样本；叠加 P0-2 真实图中人工确认的字符裁剪。
2. 模型：小型 CNN（3–4 层卷积，输入 32×32）或 MobileNetV3-small 截断，类别 ≤ 20。PyTorch 训练，导出 ONNX。
3. 推理：`onnxruntime` 加载（见 P1-2 的 Python 版本问题），替换 `TemplateClassifier.classify` 的调用点，接口签名不变（返回 `(char, confidence)`）。
4. 保留模板匹配作为无模型时的回退（与 CREPE/YIN 同款降级策略）。

**涉及文件**：`pitchlens/core/recognition.py`（分类器抽象）、新增 `pitchlens/models/`（ONNX 文件，打包进 spec）。

**验收**：真实测试集（P0-2）上音级正确率显著高于模板基线；单字符推理 < 2 ms（CPU）。

**前置**：建议先做 P0-2，否则没有评判 CNN 是否更好的基准。

## P1-2 CREPE 落地（解决 Python 3.15 依赖问题）

**现状**：默认 YIN；CREPE 适配器已写好但本机 Python 3.15 无 onnxruntime wheel，实际从未跑过。YIN 在带颤音歌声上的精度很可能达不到方案 ±20 cents 的验收指标。

**方案依据**：§2/§3 以 CREPE 小型模型为初始检测器。

**改法（0.5–1 天）**：
1. 把项目 venv 换成 Python 3.12 或 3.13（onnxruntime 有稳定 wheel），`pip install -r requirements-crepe.txt`。
2. 获取 CREPE ONNX 模型（`crepe-tiny`/`crepe-small` 转换版），放入 `pitchlens/models/`，设置页填路径或默认识别该目录。
3. 用同一段歌声录音（或合成带颤音信号）对比 YIN / CREPE：稳定段中位误差、八度错误次数、单帧耗时。
4. `PitchLens.spec` 的 `datas` 加入模型文件，确认打包体积可接受（tiny ≈ 2 MB，small ≈ 10 MB 级）。

**涉及文件**：`pitchlens/core/pitch.py`（适配器已有，只需验证）、`PitchLens.spec`、`requirements-crepe.txt`。

**验收**：CREPE 在 48k→16k 链路下端到端延迟仍满足 120–150 ms；稳定音误差达到方案指标。

**注意**：`pitch.py` 的 `_resample_linear` 是线性插值，无抗混叠。CREPE 实测不达标时第一个排查点就是把重采样换成 `scipy.signal.resample_poly`。

## P1-3 反复记号展开

**现状**：`jianpu_text.py` 把 `||`、`:|`、`:` 直接跳过；识别链路完全没提取反复记号。方案 §5.3 要求"反复记号展开后的小节顺序合法"。

**改法（1–2 天）**：
1. `Score` 增加 `play_order: list[int]`（小节播放顺序），默认顺序播放；`refresh()` 时按反复记号展开。
2. 文本解析：`|: |: ... :|` 记号解析为反复区间，嵌套/无配对 → 警告。
3. 识别链路：双线+双点的竖线组合在 `_extract` 阶段标记为 repeat barline（两条紧贴 vline + 两侧点），交给组装层。
4. `rebuild_timing()` 按展开后的顺序生成 `start_beat`，跟谱器无需改动（它只看音符序列）。

**涉及文件**：`pitchlens/core/score.py`、`jianpu_text.py`、`recognition.py`。

**验收**：含 `|: :|` 的谱展开后总时值 = 手工计算值；无配对反复记号 → 标红警告。

## P1-4 暂停后回看历史曲线

**现状**：`pitch_timeline.py` 中 `setMouseEnabled(False, False)`，暂停只能冻结当前窗口，不能拖动回看。方案 §8 阶段 1 要求"历史曲线、暂停和回看"。

**改法（0.5 天）**：
1. `set_paused(True)` 时 `plot.setMouseEnabled(True, False)`（只允许横向拖动），恢复运行时重新锁定并把 XRange 拉回 `[-history, future]`。
2. 拖动后显示一个"回到当前"浮动按钮（或复用现有"回到开头"按钮逻辑改为"回到当前时刻"）。
3. 注意 `update_view` 里每 tick 会 `setXRange` 复位——暂停期间要跳过这个复位，否则拖不动。

**涉及文件**：`pitchlens/ui/pitch_timeline.py`、`main_window.py`（`_stop_audio` 状态联动）。

**验收**：暂停后可横向拖遍全部历史；恢复演唱后视图自动回到当前时刻居中。

## P1-5 跟谱丢失时未来旋律变暗

**现状**：丢失时未来旋律停止移动（beat_position 冻结 ✓），但没有变暗（方案 §4.1 明确要求）。

**改法（半天）**：
1. `_draw_targets` 里读 `state.status`：`lost` 时 future band 的 brush/pen 透明度降到当前值的 ~40%，或换成灰色系。
2. 颜色常量放 `ui/theme.py` 的 `COLORS`，不要散落硬编码。

**涉及文件**：`pitchlens/ui/pitch_timeline.py`、`pitchlens/ui/theme.py`。

**验收**：手动制造丢失（持续唱错）→ 右侧旋律肉眼可见变暗且不动；恢复定位后还原。

## P2-1 音频时间基准改用 ADC 时间戳

**现状**：`audio.py` 用 `total_written / sample_rate` 作音频时间，丢帧会漂；`frame.audio_time` 取窗口末端，曲线位置比真实演唱时刻系统性强约半个窗口（~21 ms @2048/48k）。

**改法（0.5 天）**：
1. 回调里读 `time_info.inputBufferAdcTime`，与 `total_written` 配对存入环形缓冲（如双缓冲元数据队列）。
2. `frame.audio_time` 改为窗口中心时刻：`adc_time_of_window_end - window_size / (2 * sr)`。
3. 保留现有 `latency_offset_ms` 作为用户微调；改完后默认值应接近真实延迟。

**涉及文件**：`pitchlens/core/audio.py`。

**验收**：用已知节拍的录音（或耳机泄漏的节拍器声）验证曲线与节拍对齐误差 < 50 ms；丢帧注入测试（模拟 status 置位）时间不漂。

## P2-2 跟谱移出 UI 线程

**现状**：`follower.update` 在 `main_window._tick`（UI 线程）里逐帧跑。当前计算量小无实际影响，但与方案 §7 的线程划分不一致，后续 HMM 变复杂会卡 UI。

**改法（0.5–1 天）**：
1. 跟谱器放入 `QThread` worker，UI 通过 `Signal` 投递 `PitchFrame`（值传递，不可变），worker 回发 `FollowState`。
2. UI 只保留最新 state 用于绘制；`seek()` 通过信号发给 worker，避免跨线程直接调方法。
3. 注意 `ScoreFollower` 持有 `Score` 引用：校正应用新乐谱时要先停 worker 再 `set_score`。

**涉及文件**：`pitchlens/ui/main_window.py`、`pitchlens/core/follower.py`（无需改算法，加线程壳）。

**验收**：演唱中打开大图片识别 + 拖动窗口，fps 不掉、跟谱不卡。

## 建议实施顺序

```text
P0-2 真实测试集 ──┐
                  ├→ P1-1 CNN 分类器（有基线才能证明 CNN 更好）
P0-1 弧线止血 ────┘
P1-2 CREPE 落地（独立，随时可做）
P1-3 反复记号 → P1-4 回看 → P1-5 变暗（都是独立小项）
P2 系列穿插进行
```

先做 P0-1 止血和 P0-2 测试集：一个防错误传播，一个是后续所有识别改进的度量基础。
